# 【提醒与复习模块】核查详情与优化方案

## 1. 基础信息
- 模块/功能名称：提醒与复习（Reminder）
- 核查日期：2025-11-18
- 核心代码所在路径：
  - backend/reminder/services.py（复习计划计算、统计、触发通知）
  - backend/reminder/mongodb_models.py（提醒文档模型，未展开）
  - backend/reminder/views.py、tasks.py、routing.py（未展开）
  - 关联模块：backend/notification/services.py（创建/标记/查询/删除通知）

## 2. 功能实现结论
- 结论：具备基础的“复习待办拉取、复习完成更新下一次时间、统计”核心能力，并且试图通过 NotificationService 进行触达。但当前存在关键一致性缺陷（Reminder 调用的 schedule_notification 在 NotificationService 中不存在）、调度与时区策略不完善、并发与可靠性不足，需要补齐异步任务与推送通道、时间口径与节流、数据索引与权限等能力。

## 3. 已实现能力（概览）
- 待复习查询：get_upcoming_reviews(user_id) 在未来24小时窗口内查未完成复习事项，按时间排序。
- 复习完成：mark_as_reviewed(reminder_id) 更新 last_reviewed/review_count，随后 update_review_schedule 根据 review_interval 计算下一次时间并再次安排通知。
- 统计：get_review_statistics(user_id) 汇总总数、完成数、即将复习数与完成率。

## 4. 发现的问题（P0 优先级）
1) 通知接口不一致（功能缺陷）
- ReminderService.schedule_review_notification 使用 notification_service.schedule_notification(...)，但 NotificationService 中并无该方法，仅提供 create_notification/mark/read/list/delete。应补齐“计划/定时通知”的接口与任务实现，或改为创建定时任务队列。

2) 调度与异步
- 无明确的异步调度机制（Celery/Beat 或 APScheduler）来在 review_time 触发推送；当前仅“安排”但未落地；
- 缺失任务幂等、失败重试、死信队列与去重策略（同一 reminder 不同时间窗重复投递）。

3) 时间与时区
- 使用 datetime.now()，未统一为 timezone-aware（UTC）并按用户时区渲染；夏令时与跨区使用风险。

4) 数据与索引
- 未来24小时查询需索引：user_id、review_time、is_completed；
- 统计与批量查询在数据量较大时会退化；

5) 权限与多租户
- 仅按 user_id 过滤，未考虑组织/协作共享场景；

6) 节流与风控
- 无“频繁复习提醒”限流；
- 无每用户每日推送上限、免打扰时段（Do-Not-Disturb）；

7) 体验与功能缺失
- 无“稍后提醒（snooze）”“跳过本次”“自动间隔算法（SM-2/Anki 曲线）”“批量完成/推迟”等；
- 无“提醒链接目标”（例如跳转到相关笔记/任务详情）；

## 5. 可落地优化建议
1) 定时/异步投递（P0）
- 引入 Celery + Celery Beat：
  - Beat 周期任务扫描即将到期的提醒，派发 notify_review_task(reminder_id)；
  - 或在创建/更新 reminder 时创建一条延迟任务（ETA = review_time）；
- NotificationService 扩展 schedule_notification(user_id, title, message, scheduled_time, data) → 仅落库“待发通知”，由 Celery 轮询或定时触发发送；

2) 通知与通道（P0）
- 站内实时：Channels/WebSocket 向在线用户推送；
- 离线通道：邮件/移动推送（可选），并遵循用户偏好与免打扰；
- 去重与幂等：按 (user_id, reminder_id, scheduled_time) 去重；

3) 时间口径（P0）
- 统一使用 timezone.now()（UTC）存储，用户界面转换为其时区；
- 支持“工作时间提醒”与“跨时区迁移”策略；

4) 索引与性能（P0）
- Mongo 索引建议：
  - Reminder: (user_id, is_completed, review_time), (user_id, last_reviewed), TTL 可选；
  - Notification（待发表）：(user_id, is_read, created_at) 与（scheduled_time）复合索引；

5) 节流与风控（P1）
- 同一 reminder 在短时间内重复提醒的抖动合并（窗口 10-15 分钟）；
- 每用户每日推送上限与异常报警；

6) 复习算法（P1）
- 支持基于记忆曲线的间隔重复（SM-2/Ebbinghaus）：根据用户评分（难度/是否掌握）调整下一次间隔；

7) 体验（P2）
- 提供 snooze（+5/15/60 分钟）、跳过本次、批量完成/推迟；
- 通知 payload 带上跳转链接（对象ID、路由、CTA 按钮）。

## 6. 关键改造片段（示例）
- Celery 任务：
  - notify_review_task(reminder_id): 加载 reminder→创建并发送 Notification（含 WebSocket 推送）；失败重试；
- NotificationService.schedule_notification：
  - 写入 PendingNotification(doc) {user_id,title,message,scheduled_time,data,status='scheduled'}；
  - Beat 定时任务扫描 scheduled_time<=now 且 status='scheduled' → 发送并置 status='sent'；
- 去重幂等：
  - upsert by key = sha256(f"{user}:{reminder}:{scheduled_time}")；

—— 建议优先落地“定时/异步投递 + Notification 接口补齐 + 时区统一 + 索引与节流 + 复习算法”的 P0，随后完善体验与多通道策略，提升提醒模块的实用性与可靠性。

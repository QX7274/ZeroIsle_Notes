# 【密码重置功能】核查详情与优化方案

## 1. 基础信息
- 模块/功能名称：密码重置功能（Password Reset）
- 核查日期：2025-11-18
- 核心代码所在路径：
  - admin_system/backend/users/models.py（UserProfile、VerificationCode 模型）
  - admin_system/backend/users/services/password_service.py（PasswordService 实现）
  - admin_system/backend/users/views/password_reset.py（视图 API）

## 2. 核查结果

### 2.1 功能实现结论
- 结论：部分实现
- 已实现能力：
  - 支持通过邮箱或手机号发送重置验证码；
  - 验证验证码有效性并返回 verification_id；
  - 完成密码重置：校验 verification_id 后，调用主应用 API 重置密码，并标记验证码已使用；
  - 记录 VerificationCode（用途、过期时间、是否已使用）与 UserProfile 的密码重置时间/操作者。
- 未实现/存在缺陷：
  - 安全防护薄弱：接口 AllowAny，无验证码/人机校验、无速率限制/节流、无 IP/设备级风控；
  - 可用性风险：在调用主应用密码更新 API 之前即将验证码标记为已使用，若外部 API 调用失败则验证码被消耗且重试困难；
  - 配置/集成脆弱：requests 无超时/重试/回退策略；对 MAIN_APP_API_URL/API_KEY 依赖未做健康检查与权限最小化说明；
  - 信息泄露风险：返回“用户不存在/未绑定邮箱/手机”等差异化错误，易被用于用户枚举；
  - 密码策略缺失：new_password 未做长度/复杂度/历史重用检查；
  - 审计缺失：未记录重置请求/验证/完成的结构化审计（含 IP/UA/渠道/失败次数）；
  - 验证码管理不足：无发送频控、同一用户并发验证码策略、最大尝试次数、过期/清理机制；
  - 业务一致性：VerificationCode 与外部 API 调用无事务/补偿；
  - 国际化与多语言缺失；
  - 返回结构中的 expires_at 直接暴露具体时间，且缺时区/格式统一。

### 2.2 代码质量问题清单与改进方向
1) 权限与防护
- 问题：三个接口（发送/验证/完成）均 AllowAny；无节流/风控。
- 改进：
  - 接口权限保持 AllowAny 但加 DRF Throttle 类（基于 IP/用户标识），并接入人机校验（图形/滑块/Turnstile 等）；
  - 对管理员来源与普通来源区分严格的频率配额；
  - 增加签名/一次性 nonce 机制，避免重放。

2) 外部 API 调用的健壮性
- 问题：requests.post 未设置 timeout、无重试、未捕获请求级异常（仅大 try/except）；
- 改进：
  - 设定 timeout（连接/读取），配合指数退避重试（最多3次）；
  - 根据响应码与错误码分类处理（如429进行退避、5xx重试）。

3) 业务时序与幂等
- 问题：reset_password 先将 verification.is_used=True，再调用主应用；失败会造成验证码被消耗；
- 改进：
  - 先调用主应用成功后再置 is_used=True；
  - 或引入“使用中”状态与失效时间窗口，失败时回滚为未使用；
  - 通过 verification.version/updated_at 做乐观锁，保证幂等。

4) 错误消息与枚举风险
- 问题：区分“用户不存在/未绑定邮箱/手机”；
- 改进：
  - 对外统一提示“如账号存在，我们已发送验证码”；
  - 详细原因仅写入日志/审计。

5) 密码策略与校验
- 问题：未校验新密码安全规则；
- 改进：
  - 引入密码策略（长度、字符集、常见弱口令、历史重用限制）；
  - 将校验前置在本服务与主应用一致。

6) 验证码生命周期与频控
- 问题：缺发送频率限制、最大尝试次数、同一用途并发码；
- 改进：
  - 限制每帐号/每 IP 在时间窗口内的发送次数（如 5 次/小时）；
  - 同用户同用途仅保留最新一条有效码，或使用计数+锁定策略；
  - 验证失败次数上限（如 5 次）后冻结验证码/触发风控。

7) 审计与可观测
- 问题：仅日志，不可查询；
- 改进：
  - 新增审计模型 PasswordResetAudit：user、channel、ip、ua、action（send/verify/complete）、result、reason、trace_id；
  - 生成 trace_id 贯穿三步，便于排障；
  - 指标：发送量、成功率、失败原因分布、平均耗时。

8) 配置与安全
- 问题：API URL/Key 直接使用 settings，缺轮换/最小权限；
- 改进：
  - 使用专用 Key，权限仅允许重置密码/发信；
  - 支持密钥轮换（双 Key 窗口）与从系统设置安全读取（加密存储、脱敏回显）。

9) 返回值与时间处理
- 改进：
  - 统一时间格式（ISO8601 + 时区）；
  - 对外不返回精确过期时间，可返回相对分钟数。

### 2.3 可维护性
- 结构：当前视图逻辑清晰，但安全/风控/审计散落于各处，建议抽取 ResetFlowService（风控、审计、节流、消息模板、外部API适配）。
- 命名：请求来源 request_source 的取值建议收敛（user/admin/system），并常量化。
- 文档：补充时序图与失败补偿流程文档。

### 2.4 集成情况（与直接关联模块）
- 与主应用：通过 HTTP API 重置密码/发送验证码，缺超时/重试与响应校验；
- 与用户模块：UserProfile/VerificationCode 正常；但与主应用用户体系的 ID 类型（UUID vs ObjectId）差异需确认一致性；
- 与系统设置：可将短信/邮件开关、频控阈值、验证码长度/有效期置于 SystemSetting。

## 3. 具体优化建议（可落地操作）
1) 安全与风控（P0）
- 为三个端点添加 DRF Throttle（IP+用户维度），并接入人机校验；
- 统一对外提示消息，避免用户枚举；
- 增加最大尝试次数/失败锁定策略；
- 验证码长度与字符集可配置，默认6位数字，支持切换为数字+字母。

2) 业务幂等与补偿（P0）
- 将 verification.is_used 的更新放到主应用重置密码成功之后；
- 引入“使用中”状态与超时回滚；
- 对外返回 verification_id 的同时返回 trace_id，用于后续查询与补偿。

3) 外部调用稳健性（P0）
- requests.post 设置 timeout（(3, 10)），并使用 tenacity 等库做指数退避重试；
- 区分 4xx/5xx 与 429 的处理逻辑；
- 失败时不消耗验证码，并返回可重试建议。

4) 密码策略（P0）
- 在视图层添加新密码校验（长度≥8、至少三类字符、黑名单词库、与旧密码不同）；
- 与主应用策略对齐，并提供统一错误码。

5) 审计与监控（P1）
- 新增 PasswordResetAudit 模型与写入点；
- 导出审计报表与指标面板（成功率、失败Top原因、地区分布）。

6) 配置化（P1）
- 在 SystemSetting 增加 password_reset.*：code_length、ttl_minutes、send_limit_per_hour、require_captcha、max_verify_attempts 等；
- 接口读取并应用配置。

7) 代码整理（P2）
- 提取外部 API 客户端（带超时/重试/签名）；
- 抽象 ResetFlowService，统一风控、审计、节流、消息模板；
- 统一时间与返回结构（带时区）。

## 4. 关键代码改造建议（片段级思路）
- 幂等：
  - try 调用主应用 -> 成功后 verification.is_used=True 保存；失败则不修改或回滚；
- 速率限制：
  - 使用 DRF ScopedRateThrottle；按 IP 与 user_id 双维度进行节流；
- 统一提示：
  - 不暴露“用户不存在/未绑定”，返回“如账号存在，我们已发送验证码”；
- 请求超时与重试：
  - requests.post(..., timeout=(3, 10))；配合重试库对 5xx/网络异常重试；
- 密码校验：
  - 使用正则与黑名单库验证复杂度；

—— 本次模块核查到此结束，建议优先落地“安全与风控、幂等修复、外部调用超时重试、密码策略”，随后推进审计/配置化与代码抽象。

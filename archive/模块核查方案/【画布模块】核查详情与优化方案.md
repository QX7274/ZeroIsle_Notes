# 【画布模块】核查详情与优化方案

## 1. 基础信息
- 模块/功能名称：画布模块（Canvas）
- 核查日期：2025-11-18
- 核心代码路径：
  - MongoEngine模型：/backend/canvas/mongodb_models.py（Canvas、CanvasElement、CanvasConnection）
  - 服务：/backend/canvas/services/canvas_service.py
  - 视图/序列化器：/backend/canvas/views/*、/backend/canvas/serializers/*（未逐一展开，本次聚焦模型与服务对接）

## 2. 核查结果
### 2.1 功能实现
- 结论：部分实现（存在“ORM来源不一致导致调用不可用”的关键问题）
- 已实现（模型侧）：
  - Canvas：用户归属、标题/描述、画布尺寸/缩放/位置、模板/公开/标签、软删除标记、更新时间字段，常用索引齐备；
  - CanvasElement：元素类型、位置/尺寸、样式/属性、软删除标记，按画布ID和类型索引；
  - CanvasConnection：元素间连接（source/target/type/样式/属性）、软删除标记，按画布和端点索引。
- 服务侧（canvas_service.py）问题：
  1) ORM与模型不匹配（致命）：
     - from canvas.models import Canvas（Django ORM），而本项目有效模型为MongoEngine的 /backend/canvas/mongodb_models.py；
     - 后续所有 Canvas.objects.* 的调用均按Django ORM语义实现，无法作用于MongoEngine文档；运行期将报导入/调用错误。
  2) 关联访问错误：
     - delete_canvas 中使用 canvas.elements.all() / canvas.connections.all() 清理元素与连接，但MongoEngine的Canvas并未声明反向关系，元素/连接通过canvas_id字段关联；该调用无效。
  3) 计数字段与字段缺失：
     - increment_view_count 假设Canvas存在view_count字段，但MongoEngine版本并未定义该字段；调用将失败。
  4) 查询语法错误：
     - get_canvas_by_id 中使用 models.Q 构造条件且再次 .filter() 链式，这属于Django ORM写法；MongoEngine应使用Q与objects(user=...)/filter复用的语法或直接字典过滤。

### 2.2 代码质量
- 问题清单：
  1) 数据访问层混用：
     - 服务完全按Django ORM实现，而项目其它处（realm_*、notes、reminder等）主要使用MongoEngine；需统一。
  2) 领域关联缺乏统一入口：
     - 元素/连接的查询/删除应以canvas_id外键字段进行，当前假设反向关系存在；建议提供CanvasElementService/CanvasConnectionService统一删除/查询。
  3) 软删除一致性：
     - 模型具备is_deleted，但服务侧的删除是硬删（canvas.delete()）；是否需要统一软删策略（标记画布和元素/连接为is_deleted=True）。
  4) 并发与性能：
     - 元素/连接大量删除建议用批量操作；后续可考虑分片/分页删除与异步清理。

- 改进方向：
  - 服务层全面切换至MongoEngine：
    - from canvas.mongodb_models import Canvas, CanvasElement, CanvasConnection；
    - 查询与过滤使用MongoEngine语法，放弃Django models.Q；
  - 统一删除策略：
    - 方案A：软删除（将Canvas及其元素/连接is_deleted=True，记录deleted_at），保留恢复能力；
    - 方案B：硬删除前先批量删除元素与连接（按canvas_id过滤）；
  - 计数字段：
    - 如需要view_count，补充字段与索引；或移除increment_view_count逻辑。
  - 抽象子服务：
    - 引入CanvasElementService/CanvasConnectionService处理关联查询/批量删除/计数等，避免视图/服务层重复逻辑。

### 2.3 可维护性
- 问题：服务与模型完全脱节、删除逻辑不一致、缺少子服务抽象；
- 建议：统一ORM后补充单元测试（创建/更新/删除/查询权限、批量清理、软删/硬删策略），并补充事务性/异常回滚策略（MongoEngine无事务或使用MongoDB会话）。

### 2.4 集成情况（直接关联模块）
- 与用户模块：Canvas.user为MongoUser，需保证request.user→MongoUser映射一致（与notes/realm_*一致）；
- 与知识图谱/搜索：画布数据可选入索引或图谱（后续）；
- 与协作分享：如存在画布协作/分享，需对接权限检查与通知。

## 3. 具体优化建议（可直接落地）
1) 统一服务导入：
   - 改为 from canvas.mongodb_models import Canvas, CanvasElement, CanvasConnection；
   - 将Django风格查询替换为MongoEngine（objects/filter、Q来自mongoengine.queryset.visitor）。
2) 删除策略与实现：
   - delete_canvas：
     - 方案A软删：Canvas.is_deleted=True；CanvasElement/CanvasConnection按canvas_id批量update set is_deleted=True；
     - 方案B硬删：CanvasElement.objects(canvas_id=canvas.id).delete(); CanvasConnection.objects(canvas_id=canvas.id).delete(); 再canvas.delete()；
3) 关联访问修正：
   - 通过canvas.id→按canvas_id过滤元素和连接；
4) 视图/序列化对齐：
   - 确认视图使用MongoEngine模型与分页安全；
5) 字段一致：
   - 如需view_count，补充模型字段与$inc原子更新；否则移除相关服务方法。

## 4. 建议的改动点清单（代码级）
- services/canvas_service.py：
  - 统一导入MongoEngine模型；
  - 替换Django查询、修复删除与计数；
- mongodb_models.py：
  - 如采用view_count或deleted_at策略，补充字段与索引。

## 5. 预期影响与回滚
- 影响：画布服务可用性恢复，删除与查询可靠；
- 回滚：改动集中于canvas服务层与（可选）模型字段，建议分支小步推进并配套测试。

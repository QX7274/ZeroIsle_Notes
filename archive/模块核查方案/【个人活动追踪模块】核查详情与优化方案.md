# 【个人活动追踪模块】核查详情与优化方案

## 1. 基础信息
- 模块/功能名称：个人活动追踪（Personal Activity Tracking）
- 核查日期：2025-11-18
- 核心代码路径：
  - 后端：/backend/personal_activity/
    - 原生PyMongo模型/DAO：/backend/personal_activity/mongodb_models.py（PersonalActivityModels, ActivityRecord, ActivityCategory, ActivityGoal）
    - 视图/序列化器：/backend/personal_activity/views.py、/backend/personal_activity/serializers.py（未展开，重点聚焦数据层）

## 2. 核查结果
### 2.1 功能实现
- 结论：部分实现（存在“存储层与全局不一致、连接获取与更新语义错误”的关键问题）
- 已实现（代码存在对应逻辑）：
  - 活动记录：新增/按ID查/列表筛选（状态/分类/标签/时间窗）/更新/软删除/状态与进度更新；
  - 分类：新增/按ID查/列表/更新/软删除/为新用户创建默认分类；
  - 目标：新增/按ID查/列表（按状态）/更新/删除/进度更新（自动计算完成率并置完成）。

- 未实现/缺陷：
  1) 存储层与项目其它模块不一致（高风险）：
     - 本模块直接使用PyMongo与自建DAO；项目其它业务普遍使用MongoEngine模型（notes/search/reminder等）。
     - 导致数据访问风格、事务/校验/索引策略不统一，维护与联动复杂度高。
  2) 连接获取方式与路径错误：
     - from mongodb_service import get_mongodb_connection，项目中并无该导出方法；现有可复用连接在 backend/sync/services/mongodb_service.py（mongodb_service.db）。
     - 风险：运行期ImportError或连接多实例不一致。
  3) 索引与TTL：
     - 为 reports 集合创建 TTL 索引（expires_at, expireAfterSeconds=0），但模块内未见任何报告生成/写入expires_at逻辑；该索引名存疑且无效。
  4) 更新语义错误（必现）：
     - ActivityRecord.update 中将{"version": {"$inc": 1}}放在$set内（update_data），最终使用{"$set": update_data}，这不会自增version，反而把version字段设为对象{"$inc":1}。
     - 正确做法：在update_one时同时包含{"$set": {...}, "$inc": {"version": 1}}。
  5) 参数与类型校验缺失：
     - 列表与更新未对start_date/end_date的类型做解析与时区统一；user_id、dependencies、category_id等均按字符串直接入库后再转ObjectId，缺少格式校验与错误提示；
     - 贴图/附件/位置/天气等字段无大小/格式限制与清洗。
  6) 安全与归属：
     - DAO以user_id入参进行过滤，但未与认证身份统一（如Django用户→Mongo用户映射），也未在服务层强制校验“当前用户只能操作自己的记录”；需由视图层严密保护。
  7) 分页与限流：
     - page_size无上限，潜在DoS风险；
  8) 并发一致性：
     - 无乐观锁/条件更新（例如基于version或updated_at）；并发修改可能覆盖；
  9) 生态联动缺失：
     - 无通知触发（完成目标/达成里程碑等）、无搜索索引写入、无智能分析产出（仅索引创建有reports集合影子）。

### 2.2 代码质量
- 问题清单：
  1) 存储层割裂：自建PyMongo DAO与全局MongoEngine并存，造成风格与工具链不统一；
  2) 连接模块路径错误：mongodb_service导入不可用；
  3) 更新语义错误：version自增写法错误；
  4) 字段校验与清洗缺失：对时间、ID、列表类字段未做严格校验；
  5) 分页/上限缺失：page_size未限制且未白名单化；
  6) 可维护性：没有单元测试覆盖关键路径；
  7) 未使用统一的时区工具：混用datetime.timezone与项目普遍django.utils.timezone策略；
  8) 代码与注释中中英混排、风格不一，长期可读性受影响。

- 改进方向：
  - 统一为MongoEngine模型/或封装统一DAO层：
    - 选项A：将ActivityRecord/Category/Goal重写为MongoEngine Document，统一查询/索引/校验风格；
    - 选项B：若保留PyMongo，则抽象通用DAO封装到common数据层，并提供统一连接、错误码与日志。
  - 连接统一：
    - 共用backend/sync/services/mongodb_service.mongodb_service.db；或提供全局Mongo客户端/连接工厂；
  - 修复version自增：
    - update_one({$set: fields, $inc: {version: 1}}) 并基于version或updated_at做乐观锁；
  - 时间与时区：
    - 标准化输入（ISO 8601）并统一转换为UTC；
  - 分页安全：
    - page_size上限（如<=100），非法参数回退默认值；
  - 校验与清洗：
    - 对ObjectId、日期、枚举（status/priority/content_type）做验证；
  - 衍生联动：
    - 目标完成/里程碑达成触发通知；
    - 写入SearchIndex（关键词、内容、标签）以便检索；
    - 生成分析报告写入reports并设置expires_at配合TTL；

### 2.3 可维护性
- 问题：与全局ORM不一致导致后续改造成本高；缺测试；未来与移动端/前端协作口径不一（时间/枚举/字段）。
- 建议：先“止血”（修复连接/自增/分页/校验），再“统一”（迁移至MongoEngine或抽象DAO），最后“增强”（联动通知/搜索/报告）。

### 2.4 集成情况（直接关联模块）
- 与用户模块：需要Django用户→Mongo用户ID映射，保证user_id归属一致；
- 与通知模块：目标完成、活动达标等可触发通知；
- 与搜索模块：活动与日记内容可入索引；
- 与同步：可与Sync协议对齐（version/updated_at）。

## 3. 具体优化建议（可直接落地）
1) 连接与导入修复：
   - 将from mongodb_service import get_mongodb_connection替换为统一连接（如backend/sync/services/mongodb_service.mongodb_service.db）；
2) 更新语义修复：
   - 更新API统一使用{"$set": fields, "$inc": {"version": 1}}；必要时加条件：{"version": expected_version}实现乐观锁；
3) 分页安全：
   - 限制page_size最大100，非法值回退默认20；
4) 参数校验：
   - 对user_id/activity_id/category_id/goal_id进行ObjectId格式验证；日期参数解析ISO并转换为UTC；status/priority/content_type使用枚举；
5) 统一时区：
   - 使用UTC并在展示层转换本地；
6) 报告与TTL：
   - 若需要临时报告，新增生成逻辑并写入expires_at（UTC），TTL索引方可生效；
7) 联动与审计：
   - 目标完成/进度更新超阈值时写入通知；重要操作记录审计日志（user、action、ids、timestamp）。

## 4. 建议的改动点清单（代码级）
- mongodb_models.py：
  - 替换连接获取；
  - ActivityRecord.update修复$inc；
  - 列表查询增加page_size上限；
  - 输入校验与类型转换辅助函数；
  - 可选：迁移到MongoEngine模型定义（Activity/Category/Goal/Report）。

## 5. 预期影响与回滚
- 影响：更新正确性与稳定性显著提升；分页与类型校验加强安全；与全局模块联动更顺畅；
- 回滚：改动集中在personal_activity数据层；可分步启用（先连接与$inc→分页与校验→TTL与联动）。

# 管理后台功能基线与演进规划

> 版本：v1.0（2026-10-04）
> 分支：`feature/admin-system-functional-baseline`
> 范围：`admin_system/`（Django + DRF + mongoengine 后端，React 18 + antd 5 前端）
> 目的：在决定「留存 / 改造 / 新增」之前，先用可复验的证据把现状钉死。

---

## 0. 结论摘要

| 维度 | 实测值 | 判定 |
|---|---|---|
| 前端页面文件 | 41 个（含 6 个路由分发器） | 页面资产真实存在，约 2.1 万行 |
| 前端 service | 12 个 | 全部依赖同一 axios 实例 |
| 后端已注册 API 路由 | **127 条**（不含 `.format` 变体） | 接口面广 |
| 前端调用且后端存在 | 131 处调用命中 | 主链大体对齐 |
| **前端调用但后端不存在** | **44 处**（按 方法+路径 去重；原始调用点 47 处） | 关键断层 |
| 后端有但前端从未调用 | 29 条 | 含导出、封禁、重置密码等 |
| **后端能否启动** | **不能** | `manage.py check` 直接 AssertionError |
| 与主后端**共享**的集合 | **5 个**：`users` / `notes` / `tags` / `user_activities` / `verification_codes` | 全部口径冲突 |
| 管理端**读空集合** | 3 个：`note_categories` / `comments` / `attachments` | 数据面错位 |
| 未接入路由的页面 | 8 个 | 半成品 |

**一句话**：页面和交互是可用资产，但后端跑不起来、前后端契约有 44 处断层、且对 5 个共享集合的写入口径与主后端不一致 —— 直接上线会同时造成「功能不可用」和「数据被写坏」两类问题。

## 1. 盘点方法与证据来源

本轮所有数字均由可复现命令得出，不依赖主观判断：

1. **后端路由**：在隔离 worktree 中加载 Django 后遍历 `get_resolver()`，共 267 条 URL，其中 `api/` 前缀且去重后 **127 条**。
   （`admin_backend/urls.py` 的 `include_docs_urls` 会在导入期因缺 `coreapi` 抛错，枚举时在**内存中**注入 OpenAPI generator 绕过，未改动任何文件。）
2. **前端 service**：正则提取 `api.(get|post|put|patch|delete)` 调用，`${...}` 归一化为 `:id`。
3. **契约比对**：把前端路径与后端正则路由双侧归一化（剥离 `^ $` 锚点、`(?P<pk>...)` → `:id`）后做集合比对。
4. **模型冲突**：提取两侧所有 `meta['collection']`，取交集后逐个比对主键类型与字段名。

### 2.1 后端可运行性（阻塞项）

```bash
cd admin_system/backend && python manage.py check
# AssertionError: `coreapi` must be installed for schema support.
```

- **根因**：`admin_backend/urls.py` 用 DRF `include_docs_urls` 生成 CoreAPI schema，而 `requirements.txt` 钉的 DRF 3.16 已移除 coreapi 依赖。
- **更深一层**：即使补上 coreapi 或改用 OpenAPI，schema 生成仍会失败 —— DRF 的 `ModelSerializer` 不能直接套在 mongoengine `Document` 上，实测报 `AttributeError: 'MetaDict' object has no attribute 'concrete_model'`，涉及 `users`/`content`/`settings_api`/`logs`/`analytics` 全部序列化器。
- **影响**：`manage.py check`、`runserver`、`migrate` 全部不可用 → 后端目前**完全无法启动**，任何前端页面都拿不到数据。

### 2.2 后端有、前端从未调用的 29 条

其中价值较高、建议保留并接线：

| 路由 | 能力 |
|---|---|
| `POST /api/users/profiles/{id}/ban/` | 封禁用户（前端只有 activate/status） |
| `POST /api/users/profiles/{id}/reset_password/` | 管理员重置密码 |
| `POST /api/content/notes/export/`、`/api/logs/*/export/` | 内容与日志导出 |
| `GET /api/settings/backups/{id}/download/` | 备份下载 |
| `POST /api/sync/records/{id}/cancel/` | 取消同步 |
| `GET /api/analytics/reports/{id}/export/` | 报表导出 |

### 4.3 API 基地址配置错误（独立缺陷）

| 文件 | 取值 | 问题 |
|---|---|---|
| `services/authService.js:4` | `REACT_APP_API_URL \|\| 'http://localhost:8000/api'` | 8000 是**主后端**，其 API 在 `/api/v1/*`；管理后端在 **8001**、前缀 `/api/*` |
| `config.js:2` | `REACT_APP_API_BASE_URL \|\| 'http://localhost:8000/api'` | 同一问题，且**与上面不是同一个环境变量名** |
| `services/syncService.js:214` | `mainAppUrl: 'http://localhost:8000'` | 硬编码 |

即：12 个 service 全部继承 `authService` 的 axios 实例，默认指向主后端 8000 且前缀错误 → **默认配置下前端不可能连上任何后端**。

## 5. 数据模型冲突（关键风险）

### 5.1 共享集合总览

主后端与管理系统连的是**同一个 MongoDB 库**。集合名交集：

| 集合名 | 主后端模型 | 管理系统模型 | 冲突点 | 风险 |
|---|---|---|---|---|
| `users` | `backend/users/mongodb_models.py:User`，`id = UUIDField(primary_key=True)`（**默认 binary=True**） | `admin_system/backend/users/models.py:UserProfile`，`id = UUIDField(primary_key=True, binary=False)` | **主键二进制/字符串口径相反**；管理系统缺 `password`/`is_superuser`/`realm_*` 等字段 | **P0** |
| `notes` | `backend/notes/mongodb_models/note.py:Note`，显式 `id = UUIDField(primary_key=True)`；字段 `user`(Reference)、`is_deleted`、`vector_clock` | `admin_system/backend/content/models.py:Note`，**未声明 id**（即 ObjectId）；字段 `user_id`(String)、`status`、`note_type` | 主键类型不同；`user` vs `user_id`；无 `is_deleted`，却有 `status='deleted'` | **P0** |
| `tags` | `backend/notes/mongodb_models/tag.py:Tag`，**用户级**：`user` 必填 + `{user,name}` 唯一索引；有 `color`/`is_deleted` | `admin_system/backend/content/models.py:Tag`，**全局级**：`name` 全局 unique，无 `user` | 唯一性语义相反（用户级 vs 全局）；管理系统缺 `user`/`is_deleted` | **P0** |
| `user_activities` | `backend/common/analytics_service.py`，`user_id = StringField` | `admin_system/backend/users/models.py:UserActivity`，`user = ReferenceField(UserProfile)` | 关联字段类型不同（String vs Reference） | P1 |
| `verification_codes` | `backend/users/mongodb_models.py` + `models/verification_code.py` | `admin_system/backend/users/models.py:VerificationCode` | 字段集不同，管理端可能读到结构不匹配的文档 | P1 |

### 5.2 管理系统读/写的「幽灵集合」

以下集合**只有管理系统在用**，主 App 从不写入，因此管理端对应页面**永远显示空数据**：

| 管理系统集合 | 主 App 实际集合 | 涉及页面 |
|---|---|---|
| `note_categories` | `categories` | 分类管理 |
| `comments` | `note_comments` | 评论管理、用户详情 |
| `attachments` | `note_attachments` | 附件管理、用户详情 |

备份服务同样按错名字枚举集合（`backup_service_enhanced.py` 的 `collection_groups` 里写的是 `comments`/`attachments`/`user_profiles`/`note_shares`），导致「数据备份」实际备份不到评论与附件。

### 5.3 写路径风险（最需要先修）

`UserProfile.id` 的 `binary=False` 与主后端相反。主后端代码注释已记录过同类事故（RISK-BE-003）：字符串 `_id` 会让引用反解抛 `DoesNotExist`。管理端「新建用户 / 重置密码 / 改状态」都会写入 `users`，**一旦执行就可能污染主库用户主键**。

| 系统配置/公告/备份 | 3 | **保留** | 已对齐 |

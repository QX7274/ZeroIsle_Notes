# 管理后台数据口径迁移手册（阶段3 闭环）

> 版本：v1.0（2026-10-04）
> 目的：把阶段3 的**代码口径对齐**落实到**数据口径对齐**，并给出可复验的核查与回滚流程。

---

## 0. 为什么需要这份手册

阶段3 修的是**模型定义**（主键类型、集合名），但代码改动**不会修正库里已有的数据**。
危险的状态不是"数据没迁移"，而是"**以为已经迁移好了**"。
本手册提供：(1) 客观核查工具；(2) 迁移步骤；(3) 回滚方案。

### 关键事实：谁写坏了数据？

先厘清责任边界，避免迁移时误伤：

| 事实 | 证据 | 推论 |
|---|---|---|
| 管理后台在阶段2 之前**根本无法启动** | `manage.py check` 抛 `AssertionError`（阶段2 实测） | 它不可能写过任何数据 |
| 管理后台**从未能登录** | `authenticate()` 抛 `ImproperlyConfigured`，DB 引擎为 `dummy`（阶段4 实测） | 无管理员会话 → 无写操作 |
| 管理后台不在任何部署配置中 | Dockerfile / compose / nginx / CI 均无 `admin_system` | 从未在生产运行过 |

**结论：异构主键的既有数据来自主后端自身的历史实现，而非管理后台。**
主后端 `backend/users/mongodb_models.py` 的注释明确记录了同一缺陷（RISK-BE-003），
并已提供迁移脚本 `backend/scripts/migrate_user_uuid_to_binary.py`。

因此**迁移工作应当复用主后端已有的脚本**，而不是为管理后台另写一个——
两者操作的是同一批集合，另写一个只会有重复执行、互相冲突的风险。

## 1. 阶段3 改动了什么（需要迁移的部分）

| 集合 | 改动 | 是否需要数据迁移 |
|---|---|---|
| `users` | `UserProfile.id` 去掉 `binary=False` | **是**：既有字符串 `_id` 用户需改写为 Binary |
| `notes` | `Note` 补 `UUIDField` 主键（原为 ObjectId） | **是**：既有 ObjectId 文档需改写 |
| `tags` | `Tag` 补 `UUIDField` 主键（原为 ObjectId） | **是** |
| `user_activities` | `UserActivity` 补 `UUIDField` 主键 | **是** |
| `verification_codes` | `VerificationCode` 补 `UUIDField` 主键 | **是** |
| `comments` → `note_comments` | 集合改名 | **否**（改名不搬运数据；旧集合若为空则忽略） |
| `attachments` → `note_attachments` | 集合改名 | **否**（同上） |

> 说明：`users` 一项与主后端 RISK-BE-003 是同一件事，
> `backend/scripts/migrate_user_uuid_to_binary.py` 已覆盖 `users._id` 及其**所有指向 User 的引用**。
> 其余集合（notes/tags/user_activities/verification_codes）的主键改写覆盖面需在正式迁移前单独确认——
> **本手册不对未经验证的覆盖面作承诺**，请以第 2 步的核查结果为准。

## 2. 第一步永远是核查（只读）

新增的核查工具（只读，绝不写数据）：

```bash
cd admin_system/backend
python -m scripts.check_shared_collection_consistency
```

输出示例（合成数据演示）：

```
数据库: zeroislenotes
--------------------------------------------------------------------
users                  OK               total=1   binary_uuid=1
notes                  MISSING          total=0
tags                   NEEDS_MIGRATION  total=1   objectid=1
user_activities        MISSING          total=0
verification_codes     MISSING          total=0
note_comments          NEEDS_MIGRATION  total=1   string_uuid=1
note_attachments       MISSING          total=0
--------------------------------------------------------------------
结论: 需要迁移 —— tags, note_comments
```

退出码：`0` = 无需迁移；`1` = 存在异构主键；`2` = 连接/配置错误。
**可直接接入上线门禁**：退出码非 0 时阻止发布。

加 `--json` 可输出结构化结果，便于流水线解析。

环境变量（与主后端/管理后台既有命名都兼容）：
`MONGO_URI`，或 `MONGO_HOST` / `MONGO_PORT` / `MONGO_DB_NAME`（旧名 `MONGO_DB`）/ `MONGO_USER` / `MONGO_PASSWORD`。

## 3. 迁移步骤（必须在有备份的前提下执行）

```bash
# 步骤 1：备份（必须；覆盖所有将被改写的集合）
mongodump --uri="$MONGO_URI" --collection=users --out=/backup/$(date +%F)
mongodump --uri="$MONGO_URI" --collection=notes --out=/backup/$(date +%F)
mongodump --uri="$MONGO_URI" --collection=tags  --out=/backup/$(date +%F)

# 步骤 2：dry-run 复核计划（默认就是 dry-run，不写库）
cd backend
python -m scripts.migrate_user_uuid_to_binary

# 步骤 3：确认计划无误后再执行
python -m scripts.migrate_user_uuid_to_binary --apply

# 步骤 4：复验 —— 核查工具应显示 OK/EMPTY，且 dry-run 计划为空
cd ../admin_system/backend
python -m scripts.check_shared_collection_consistency
cd ../../backend && python -m scripts.migrate_user_uuid_to_binary   # 应为 0/0
```

主后端迁移脚本的既有安全保证（见其 docstring 与 `backend/scripts/tests/`）：

- **默认 dry-run**，只有 `--apply` 才写；
- **幂等**：第二次执行计划为空；
- **失败不吞异常**，写入异常向上抛并带集合/文档 id；
- 改写方式为「备份 → 删旧 → 插新 → 删备份」——任何瞬间都不存在同 `username` 两条，
  因此不会撞 `users.username` 唯一索引，**无需 drop/recreate 索引**；
- 唯一索引冲突、同名类遮蔽（`notes.mongodb_models_legacy` 等）等已知真实库风险均已加固。

---

## 4. 回滚

首选 `mongorestore --drop` 从步骤 1 的备份恢复。

迁移脚本自身在改写期间也使用备份集合 `user_uuid_migration_backup`：
中途失败时会用备份回滚并抛出原始异常。

---

## 5. 上线顺序要求

**模型改动与数据迁移必须配套上线**。顺序：

1. 先备份；
2. 执行数据迁移；
3. 核查工具确认全部 `OK`/`EMPTY`；
4. 再部署带新模型定义的代码。

若顺序颠倒（先上代码后迁数据），期间任何"按 Binary UUID 查字符串 `_id`"的操作都会查不到记录。

## 6. 尚未验证的部分（诚实声明）

- **本手册的迁移步骤未对任何真实库执行过**。核查工具的判定逻辑有 14 条测试覆盖，
  但"真实库迁移后的反解正确性"需在预发环境实测。
- **覆盖面无承诺**：`migrate_user_uuid_to_binary.py` 对 `users` 及其引用的覆盖面有测试证据；
  对 `notes`/`tags`/`user_activities`/`verification_codes` 的**文档主键**改写是否完整，
  须由第 2 步核查结果确认；若核查显示这些集合存在异构主键而迁移脚本未处理，
  需要先扩展脚本再执行。
- 本机无 mongod，无法端到端验证；所有结论来自代码、合成数据与既有测试证据。

# 生产环境管理员身份存储方案选型

> 版本：v1.0（2026-10-04）
> 结论：**推荐方案 B（复用主后端的 users 集合与自定义 JWT）**，但需先满足 3 个前提。
>
> **2026-10-04 更新：方案 B 已实施完毕**，见《管理后台宿主与鉴权隔离评估》第 6 节。
> 本文档保留为选型依据与决策记录。

---

## 0. 结论先行

| 方案 | 含义 | 判定 |
|---|---|---|
| A | 管理后台自带 SQL 库，启用 `django.contrib.auth` | 可行但次优 |
| **B** | **管理员 = 主后端 users 集合中 `is_staff=True` 的用户，复用主后端自定义 JWT** | **推荐** |
| C | 独立的管理员集合 + 自建 JWT 签发 | 仅在有强隔离要求时选 |

**推荐 B 的核心理由（全部有代码/测试证据）**：

1. **主后端已经把这套东西建好并测过**——`is_staff`/`is_superuser` 字段、
   `users.jwt_auth.CustomJWTAuthentication`、`common/mongo_user.get_mongo_user`
   身份统一层、`IsOwnerOrAdmin` 权限类，且 `backend/users/tests/` 下有
   `test_jwt_auth.py`、`test_auth.py`、`test_middleware.py`、`test_profile_permissions.py` 等成套测试。
2. **本项目已经在身份口径上踩过坑并填平**——RISK-BE-003（字符串 `_id` vs Binary UUID）、
   RISK-BE-004（Django User 直接塞进 mongoengine ReferenceField）、RISK-BE-015
   （`obj.user == request.user` 跨类型恒为 False）。选 A 或 C 等于**换一套身份体系再踩一遍**。
3. **管理后台要管的就是主后端的数据**——它读写同一个 `users` 集合。
   若管理员是另一套体系里的账号，就必须持续维护"管理账号 ↔ 业务用户"的映射，
   这个映射本身没有业务价值。

## 1. 三个方案对比

| 维度 | A：自带 SQL 库 | **B：复用主后端** | C：独立管理员集合 |
|---|---|---|---|
| 新增基础设施 | 需一个 SQL 实例 | **无** | 无（用同一 MongoDB） |
| 身份体系数量 | 3 套（主后端 + 管理 SQL + 误用的 mongoengine UserProfile） | **收敛为 1 套** | 2 套 |
| 复用主后端 JWT | 否 | **是** | 否 |
| 复用权限体系 | 否 | **是** | 否 |
| 与业务数据的关联 | 需自建映射 | **天然一致** | 需自建映射 |
| 隔离强度 | 强（物理隔离） | 中（逻辑隔离） | 强 |
| 改动量 | 中（建库+迁移+改鉴权） | **小-中（换认证类+权限类）** | 大（自建签发/校验/轮换） |
| 主要风险 | 两套账号需长期同步 | 管理员与业务用户共库，需靠 `is_staff` + 管理面隔离兜底 | 重复实现 JWT 易出错 |

---

## 2. 为什么"现状"是最差的

当前管理后台同时存在**三套身份概念**，且互不关联：

| 用途 | 实现 | 问题 |
|---|---|---|
| 登录鉴权 | Django ORM `django.contrib.auth.models.User`（`auth_api/views.py:6,58`） | DB 引擎为 `dummy` → `authenticate()` 抛 `ImproperlyConfigured`，**永远登录不进来** |
| 权限判定 | `IsAdminUser`（依赖 ORM 用户）、`request.user.has_perm(...)`（依赖不存在的权限表） | 同样不可用 |
| 被管理的对象 | mongoengine `UserProfile`（`collection="users"`） | 与登录用的 User 无任何关联 |

这不是"三选一"的问题，而是**必须先收敛到一套**。B 之所以最优，是因为它收敛到的
正是已经可用、已被测试覆盖的那一套。

## 3. 采纳方案 B 的前提与实施要点

### 前提（不满足则不要动手）

1. **确认业务上需要管理后台**。阶段1 基线显示 41 个页面中只有 28 个能接入，
   且 `Dashboard`、`DataAnalytics`、`ReportGenerator` 等为重复或 mock 实现。
2. **确认管理面的暴露面要求**。B 是逻辑隔离（同一数据面），
   若有"管理面必须与业务面物理隔离"的合规要求，应选 A 或 C。
3. **先完成阶段3 的数据迁移**。管理员的 `is_staff` 标记要写到 `users` 集合，
   而该集合当前可能仍有异构主键（见迁移手册）。

### 实施要点（本轮未实施，供后续执行）

| # | 动作 | 涉及文件 |
|---|---|---|
| 1 | DRF 认证类换成主后端 JWT（`users.jwt_auth.CustomJWTAuthentication`） | `admin_backend/settings.py` 的 `REST_FRAMEWORK` |
| 2 | 移除对 `django.contrib.auth.models.User` 的依赖 | `auth_api/views.py:6`、`auth_api/serializers.py:2` |
| 3 | 登录改为校验 `users` 集合中的用户 + `is_staff` 判定 | `auth_api/views.py` 的 `LoginView` |
| 4 | `IsAdminUser` 换成基于 `is_staff`/`is_superuser` 的自定义权限类 | `users/views.py:28`、`sync/views.py:17` |
| 5 | `analytics/permissions.py` 的 `has_perm()` 改为读主后端权限语义 | `analytics/permissions.py` |
| 6 | 管理面独立入口（子域名/端口）+ 实现 `ADMIN_ALLOWLIST_IPS` 中间件 | 新增中间件 + 部署配置 |
| 7 | 关闭 `CORS_ALLOW_ALL_ORIGINS`，改显式来源白名单 | `admin_backend/settings.py:210` |
| 8 | 补端到端测试：管理员可登录 / 非 staff 被拒 / 白名单外 IP 被拒 | `tests/` |

### 关于 `ADMIN_ALLOWLIST_IPS`

该变量目前在 `.env.example:44` 声明，但**全仓无任何代码读取**（阶段4 实测）。
它必须在第 6 步随管理面独立入口一起实现，单独加它没有意义——
当前连登录都进不来，IP 白名单拦不到任何东西。

## 4. 何时应改选 A 或 C

| 场景 | 建议 |
|---|---|
| 有合规要求"管理员账号不得与业务用户同库" | A（自带 SQL 库，物理隔离） |
| 管理员需独立审计留痕且不能与业务身份混淆 | C（独立集合） |
| 管理后台最终要脱离本项目独立交付 | A |
| 多数情况（本项目的现状） | **B** |

  更划算的选择是**归档管理后台**而非继续投入。

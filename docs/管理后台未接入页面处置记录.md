## 1. 已接入的三个页面

### SyncSettings —— 优先级最高

**这是本轮最重要的发现**：`SyncSettings.js` 是 `syncService` 的**唯一**消费方，
而 `syncService` 对接的是后端 `/api/sync/*` 下的 **10 个接口**
（records 的 list/detail/cancel/execute/statistics/status，
configs 的 list/detail/all_configs/update_configs）。

也就是说：在本次接入之前，**整块"数据同步管理"后端能力没有任何入口可达**，
既没有路由也没有菜单项。这不是"页面没挂上"，而是"功能整体不可用"。

### SecuritySettings / GeneralSettings

两者分别对接 `/settings/system/by_key/` 与 `/settings/system/batch_update/`、
`/settings/system/all_configs/` 与 `/settings/system/update_config/`，
均为真实存在的后端接口，且与已接入的 `SystemConfig` 不重复（侧重点不同）。

同时补齐了侧边栏菜单项与面包屑映射（含图标），保证入口可达、路径可读。

---

## 2. AdminManagement：暂不接入（后端功能缺失）

该页面调用 `/settings/admins` 与 `/settings/roles`，但**后端完全没有这两个接口**
（阶段1 基线与本轮四次端点扫描均可确认：`settings_api/urls.py` 只注册了
`system` / `announcements` / `backups`）。

页面内部对这两个接口还有 mock 兜底，若直接接入，用户会看到一份**假的管理员列表**，
比不接入更糟。因此结论是：**先补后端，再接入**。

补后端时需要注意：管理员身份在方案 B 下就是 `users` 集合中 `is_staff=True` 的用户，
因此 `/settings/admins` 应作为该集合的受控视图实现，而不是新引入一套管理员表。

---

## 3. 不接入的四个页面：与已接入页面重复，且部分为纯 mock

| 页面 | 与谁重复 | 额外问题 |
|---|---|---|
| `DataAnalytics/index.js` | `Analytics/*`（已接入 6 个子页） | 调用的 `/stats/dashboard` 等接口不存在 |
| `ReportGenerator/index.js` | `Analytics/ReportList` + `ReportTemplates` | **整页为 mock**：fetchTemplates / fetchReportHistory 全是 setTimeout 假数据，无任何 service 调用 |
| `SystemSettings/AnnouncementManagement.js` | `AnnouncementList`（已接入） | axios 调用**全部被注释**，纯 mock |
| `SystemSettings/BackupSettings.js` | `BackupManagement`（已接入） | 同上，纯 mock |

处置原则：**同一功能只保留一个可用实现**。这四页保留源码以备参考，
但不接入路由 —— 接入只会让用户看到重复入口与假数据。

若后续确认要替换现有实现，应先删除旧的、再接入新的，而不是两边并存。

---

## 4. 如何防止再次出现悬空页面

本轮新增了导航一致性测试（`src/__tests__/navigation.test.js`），
但它守的是"菜单项都有路由"这一个方向。反向（"有页面但无路由"）建议后续补一条同类检查：

扫描 `src/pages/**/*.js`，凡是被 `import` 但未被任何 `<Route>` 引用的组件即告警。
本轮未实现该反向检查，原因是当前仍有 4 个"有意不接入"的页面，
需要先建立白名单（记录在本文件中）才不会误报。

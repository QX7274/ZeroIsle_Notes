# 管理后台宿主与鉴权隔离评估（阶段4）

> 版本：v1.0（2026-10-04）
> 状态：**评估完成，未实施改造**（结论：需先做架构决策，不宜直接动手）
> 目的：确定管理功能的技术宿主路径，并让 `ADMIN_ALLOWLIST_IPS` 真正生效。

---

## 0. 结论摘要

阶段4 在开工前先做可行性核实，结果发现管理后台的鉴权链**从根上不成立**，
远超"加一个 IP 白名单"的范围。因此本阶段交付**评估与决策建议**，而非代码改造。

| 核心发现 | 证据 | 影响 |
|---|---|---|
| 管理后台的 Django 数据库引擎是 `dummy` | `admin_backend/settings.py:92-96` | Django ORM 不可用，auth 表根本无法创建 |
| 登录走 `authenticate()` + `django.contrib.auth.models.User` | `auth_api/views.py:6,58` | 实测抛 `ImproperlyConfigured`，**管理员永远登录不进来** |
| 权限用 `IsAdminUser` 与 `has_perm()` | `users/views.py:28`、`analytics/permissions.py` | 同样依赖不可用的 ORM 用户与权限表 |
| `ADMIN_ALLOWLIST_IPS` 从未被读取 | 全仓仅 `.env.example:44` 出现一次 | 是"死配置"，从未生效 |
| 管理后台与主后端共用 `users` 集合 | 阶段1/阶段3 已核实 | 两套身份体系指向同一集合，语义冲突 |

**一句话**：管理后台目前不是"缺一个白名单"，而是**核心鉴权链不可用**；
在选定宿主方案之前，任何 `ADMIN_ALLOWLIST_IPS` 之类的加固都是无意义的。

## 1. 关键证据（实测）

### 1.1 Django 数据库引擎为 dummy

```python
# admin_system/backend/admin_backend/settings.py:92-96
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.dummy',  # 使用dummy引擎，因为我们使用mongoengine
    }
}
```

`dummy` 引擎意味着 Django ORM 没有任何真实后端。
但 `INSTALLED_APPS` 里仍然包含 `django.contrib.auth`（`settings.py:37`），
而 `admin_system/README.md` 还指引用户执行 `python manage.py migrate` —— 这两条都不可兑现。

### 1.2 管理员登录链不可用（实测）

登录视图 `auth_api/views.py:58` 使用：

```python
user = authenticate(username=username, password=password)
if user is not None and user.is_staff:
```

而 `authenticate()` 操作的是 Django ORM 的 `User` 模型。实测：

```
DB engine: django.db.backends.dummy
create_superuser FAILED: ImproperlyConfigured
  settings.DATABASES is improperly configured. Please supply the ENGINE value.
authenticate FAILED: ImproperlyConfigured
  settings.DATABASES is improperly configured. Please supply the ENGINE value.
```

**即：管理后台的管理员账号在当前配置下既无法创建、也无法登录。**
这也解释了为什么该系统的鉴权问题此前从未被暴露——它从未真正被走通过。

### 1.3 权限类同样依赖不可用的 ORM

- `users/views.py:28`、`sync/views.py:17` 使用 `IsAdminUser`（依赖 ORM `User.is_staff`）；
- `analytics/permissions.py` 的三个权限类使用 `request.user.has_perm(...)`，
  依赖 Django 的权限表（同样不存在）；
- `users/views/password_reset.py:52,171` 判断 `request.user.is_staff`。

### 1.4 ADMIN_ALLOWLIST_IPS 是死配置

```bash
$ grep -rn "ADMIN_ALLOWLIST" --include="*.py" --include="*.yml" --include="*.env*" . \
    --exclude-dir=node_modules --exclude-dir=.git
./.env.example:44:ADMIN_ALLOWLIST_IPS=127.0.0.1
```

全仓仅此一处出现——它被写进了示例环境变量，但**没有任何代码读取过它**。

### 1.5 两套身份体系指向同一集合

- 鉴权用：Django ORM `django.contrib.auth.models.User`（建在 SQL 表里）；
- 管理对象：mongoengine `UserProfile`（`meta.collection = "users"`，即 MongoDB 的 users 集合）；
- 主后端的真实用户也在这同一个 `users` 集合里（阶段1/阶段3 已核实其主键为 Binary UUID）。

**三者语义完全不同却指向同一份数据**：一个"能登录的管理员"与一个"被管理的用户"，
在当前设计里没有任何关联关系。

## 2. 为什么本轮不直接改造

要把阶段4 真正做完，至少需要先决定以下三件事，且每一件都会牵动主后端：

1. **管理员身份存哪里？**
   - 方案 A：管理后台自带 SQL 库（`django.contrib.auth` 正常启用）——管理员与用户彻底分离，
     与主后端零耦合；但需要新增一个数据库依赖与迁移链。
   - 方案 B：管理员就是主后端 users 集合里 `is_staff=True` 的用户——复用主后端自定义 JWT，
     但需要把管理后台的鉴权从 Django ORM 换成主后端的认证中间件。
   - 方案 C：独立的管理员集合（mongoengine Document），自建 JWT 签发与校验。
2. **权限模型谁说了算？** 现有 `has_perm()` 依赖 Django 权限表，
   而主后端用的是自建权限体系（`backend/users/permissions.py`）。
3. **管理面与主数据面如何隔离？** 独立域名/端口 + IP 白名单，还是复用主后端挂 `/admin` 前缀。

这些都是架构决策，涉及主后端改动，**不属于"可以顺手做掉"的范围**。
在没有决策前动手，最可能的结果是造出第三套并行的身份体系，
把问题从"不可用"升级为"不可用且更复杂"。

---

## 3. 建议的决策顺序

| 步骤 | 内容 | 前置依赖 |
|---|---|---|
| 1 | 确认业务上是否真的需要管理后台（阶段1 显示 41 个页面中仅 28 个可接入） | 无 |
| 2 | 若需要，在上述 A/B/C 中选定管理员身份方案 | 步骤 1 |
| 3 | 按选定方案打通登录链，并补一条"管理员可登录"的端到端测试 | 步骤 2 |
| 4 | 再实施管理面隔离：独立入口 + `ADMIN_ALLOWLIST_IPS` 生效 + 关闭 `CORS_ALLOW_ALL_ORIGINS` | 步骤 3 |
| 5 | 权限模型与主后端对齐（复用自建权限体系，弃用 `has_perm`） | 步骤 3 |

## 4. 若采纳"方案 B"（推荐）的实施要点（供后续参考，本轮未做）

推荐方案 B 的理由：主后端已经有一套**可用的**自定义 JWT 认证体系
（`backend/users/jwt_auth.py`、`backend/common/middleware/dev_auth_middleware.py`），
并且已经解决了 UUID 主键、权限中间件等本项目踩过的坑；管理后台复用它可以避免重造。

实施要点：

1. 管理后台 `AUTHENTICATION_BACKENDS` / DRF 认证类改为复用主后端 JWT；
2. 移除对 `django.contrib.auth.models.User` 的依赖（`auth_api/views.py:6`）；
3. `IsAdminUser` 替换为基于主后端 `is_staff` 语义的自定义权限类；
4. `analytics/permissions.py` 的 `has_perm()` 改为读主后端权限体系；
5. 关闭 `CORS_ALLOW_ALL_ORIGINS`（`settings.py:210`），改为显式来源白名单；
6. 新增管理面入口（独立端口或子域名）并实现 `ADMIN_ALLOWLIST_IPS` 校验中间件；
7. 补端到端测试：管理员可登录、非管理员被拒、白名单外 IP 被拒。

## 5. 残留风险

| 风险 | 说明 |
|---|---|
| 管理后台当前完全不可登录 | 任何依赖"已登录管理员"的功能都无法验证，阶段1 报告的页面状态仅到"接口是否存在"层面 |
| `ADMIN_ALLOWLIST_IPS` 仍为死配置 | 本轮未激活；在方案落地前它不会有任何作用 |
| `CORS_ALLOW_ALL_ORIGINS = True` 仍开启 | `settings.py:210`，管理后台暴露面不受限 |
| 阶段3 的写路径风险仍在 | 主键口径已对齐，但历史字符串 `_id` 数据未迁移；在方案落地前不应投产 |
